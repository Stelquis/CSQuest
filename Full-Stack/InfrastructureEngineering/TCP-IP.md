## 一、先建立全局视角：TCP/IP 到底是什么
TCP/IP 不是单独两个协议，而是一整套互联网通信协议族。

其中：

- **IP** 负责“把数据包尽可能送到目标主机”；

- **TCP** 负责“在两端之间提供可靠、有序的字节流”；

- **UDP** 负责“以更低开销发送独立报文”；

- **DNS、HTTP、TLS、DHCP、ICMP、ARP** 等协议，各自解决名称解析、网页传输、加密、地址分配、诊断和邻居发现等问题。
可以把一次网络通信理解为寄快递：

- 应用层决定“寄什么”；

- 传输层标明“交给哪个进程”，并决定是否需要可靠送达；

- 网络层填写“源地址和目的地址”，规划跨网络路径；

- 链路层负责“在当前这一跳上交给谁”；

- 物理介质最终把比特变成电信号、光信号或无线电波。
**一句话概括：TCP/IP 的核心，就是分层协作。每一层只解决自己范围内的问题，并向上一层提供稳定接口。**

## 二、TCP/IP 四层模型与 OSI 七层模型
工程实践中，最常见的是 TCP/IP 四层模型；教材里也经常使用五层模型，把物理层从网络接口层中单独拆出。

| TCP/IP 四层 | 常见协议与技术 | 主要职责 | 对应 OSI 层 |
| --- | --- | --- | --- |
| 应用层 | HTTP、HTTPS、DNS、SSH、SMTP、DHCP | 定义应用之间如何交换数据 | 应用层、表示层、会话层 |
| 传输层 | TCP、UDP、QUIC 所依赖的 UDP | 进程到进程通信、可靠性、流量控制 | 传输层 |
| 网际层 | IPv4、IPv6、ICMP、IPsec | 跨网络寻址与路由 | 网络层 |
| 网络接口层 | Ethernet、Wi-Fi、ARP、NDP | 当前链路上的帧传输与邻居寻址 | 数据链路层、物理层 |

### 2.1 为什么一定要分层
分层带来三个直接好处：

- 1. **解耦**：HTTP 不需要知道底层是 Wi-Fi、光纤还是蜂窝网络。

- 2. **复用**：TCP 可以承载 HTTP、SSH、数据库连接等多种应用协议。

- 3. **可演进**：IPv4 可以逐步迁移到 IPv6，应用层通常不必整体重写。

### 2.2 数据在各层叫什么
同一段应用数据，经过不同层时名称会变化：

```
应用数据 Data
↓ 加上传输层首部
TCP 段 Segment / UDP 数据报 Datagram
↓ 加上 IP 首部
IP 数据包 Packet
↓ 加上链路层首部和尾部
以太网帧 Frame
↓
比特流 Bits
```
这个过程叫 **封装**；接收端反向拆除各层首部，叫 **解封装**。

```

应用数据
加 TCP/UDP 首部
加 IP 首部
加以太网首部与尾部
在介质上传输
接收端逐层解封装

```

## 三、一次网页请求，究竟经历了什么
假设你在浏览器中访问：

```
https://www.example.com/
```
从按下回车到页面显示，通常会经历下面这些阶段。

### 3.1 解析域名
浏览器需要先把 `www.example.com` 解析成 IP 地址。它可能依次查询：

- 1. 浏览器 DNS 缓存；

- 2. 操作系统缓存；

- 3. 本机 `hosts` 文件；

- 4. 配置的递归 DNS 服务器；

- 5. 必要时由递归服务器继续访问根、顶级域和权威 DNS 服务器。
DNS 不只使用 UDP。普通查询常用 UDP；遇到响应过大、区域传送或某些特定情况时会使用 TCP。现代环境中还可能使用 DoT、DoH 或 DoQ。

### 3.2 判断目标是否在同一子网
主机会用自己的 IP 地址和子网掩码计算：目标 IP 与自己是否属于同一网络。

- 在同一子网：直接寻找目标主机的链路层地址；

- 不在同一子网：把帧交给默认网关，但 IP 包的目的地址仍然是远端服务器。
这是一个非常重要的认知：

**MAC 地址负责当前一跳，IP 地址负责端到端。路由转发时，链路层地址通常每一跳都会变化，源/目的 IP 通常保持不变；经过 NAT 时 IP 或端口才可能被改写。**

### 3.3 获取下一跳的 MAC 地址
在 IPv4 网络中，主机会通过 ARP 查询“某个 IPv4 地址对应哪个 MAC 地址”。

在 IPv6 网络中，不再使用 ARP，而是通过基于 ICMPv6 的邻居发现协议 NDP 完成类似工作。

### 3.4 建立 TCP 连接
如果是传统 HTTPS，客户端通常先与服务器的 443 端口完成 TCP 三次握手。

### 3.5 完成 TLS 握手
客户端验证证书、协商加密套件和密钥，然后建立加密通道。此后中间设备通常能看到 IP、端口、流量大小和时序，但看不到明文 HTTP 内容。

### 3.6 发送 HTTP 请求并接收响应
浏览器发送请求，服务器返回 HTML。浏览器解析 HTML 后，还可能继续请求 CSS、JavaScript、图片、字体和接口数据。

### 3.7 连接复用或关闭
HTTP/1.1 可以使用持久连接；HTTP/2 在一条 TCP 连接上复用多个流；HTTP/3 则运行在 QUIC 之上，QUIC 通常基于 UDP，并集成了加密与多流传输能力。

整个过程可以抽象为：

```
Web 服务器网关/路由器DNS浏览器Web 服务器网关/路由器DNS浏览器查询域名返回服务器 IPARP/NDP 获取下一跳地址TCP 三次握手TLS 握手HTTP 请求HTTP 响应复用连接或发起关闭
```

## 四、链路层：数据如何走完“当前这一跳”
链路层解决的是同一链路或同一二层广播域中的传输问题。

### 4.1 MAC 地址
以太网常用 48 位 MAC 地址标识网络接口，例如：

```
00:1A:2B:3C:4D:5E
```
MAC 地址并不负责全球范围的路由。路由器每转发一次 IP 包，通常都会重新封装链路层帧，并使用新的源 MAC 和目的 MAC。

### 4.2 交换机做什么
二层交换机根据 MAC 地址表转发以太网帧：

- 已知目的 MAC 在哪个端口：定向转发；

- 未知目的 MAC：在同一 VLAN 内泛洪；

- 广播帧：在同一广播域内转发；

- 收到源 MAC 后：学习“该 MAC 位于哪个端口”。
现实中的很多设备是多层交换机，也能执行三层路由，因此“交换机只工作在二层”只是入门阶段的简化说法。

### 4.3 ARP 的工作方式
ARP 请求通常是广播：

```
谁是 192.168.1.1？请告诉 192.168.1.20。
```
拥有该 IP 的设备返回自己的 MAC 地址。主机把结果放入 ARP 缓存，避免每次通信都广播查询。

常用命令：

```
# Linux
ip neigh

# Windows
arp -a
```

### 4.4 VLAN：在一套物理网络上划分多个逻辑网络
VLAN 可以把同一套交换基础设施划分为多个二层广播域。不同 VLAN 之间通信通常需要三层设备路由。

VLAN 能减少广播范围、隔离网络并改善管理，但它不是完整的安全方案。真正的访问控制还需要 ACL、防火墙、身份认证等机制。

### 4.5 MTU：一帧最多能装多少网络层数据
MTU 是链路能承载的最大网络层报文大小。普通以太网接口常见 MTU 为 1500 字节，但隧道、VPN、云网络、PPPoE 和巨型帧环境可能不同。

以“以太网 MTU 1500、IPv4 首部 20 字节、TCP 首部 20 字节且均无选项”为例：

```
TCP MSS = 1500 - 20 - 20 = 1460 字节
```
IPv6 基础首部为 40 字节，所以在相同条件下常见 MSS 为 1440 字节。实际值还会受到 TCP 选项、隧道封装和路径 MTU 的影响。

## 五、IP 层：寻址、路由与“尽力而为”
IP 提供的是无连接、尽力而为的数据包传输。

所谓“尽力而为”意味着 IP 本身不保证：

- 一定到达；

- 按顺序到达；

- 只到达一次；

- 延迟稳定；

- 带宽固定。
这些能力要么由上层协议补充，要么由应用自行处理。

### 5.1 IPv4 地址与子网掩码
IPv4 地址共 32 位，例如：

```
192.168.10.77
```
CIDR 写法：

```
192.168.10.77/27
```
`/27` 表示前 27 位是网络前缀，对应子网掩码：

```
255.255.255.224
```
最后一个八位组的块大小为：

```
256 - 224 = 32
```
因此子网边界是 0、32、64、96……`77` 落在 64～95 这个范围内：

```
网络地址：192.168.10.64
广播地址：192.168.10.95
传统可用主机范围：192.168.10.65 ～ 192.168.10.94
```

### 5.2 常见 IPv4 地址范围

| 用途 | 地址范围 |
| --- | --- |
| 私有地址 | 10.0.0.0/8 |
| 私有地址 | 172.16.0.0/12 |
| 私有地址 | 192.168.0.0/16 |
| 回环地址 | 127.0.0.0/8，常用 127.0.0.1 |
| 链路本地地址 | 169.254.0.0/16 |
| 默认路由 | 0.0.0.0/0 |

私有地址不能直接在公网路由，通常需要通过 NAT 访问互联网。

### 5.3 IPv4 首部里有什么
IPv4 首部的关键字段包括：

- 版本号与首部长度；

- 总长度；

- 标识、分片标志和分片偏移；

- TTL；

- 上层协议号，如 TCP 为 6、UDP 为 17；

- 首部校验和；

- 源 IP 与目的 IP；

- 可选字段。
其中 TTL 尤其重要。

### 5.4 TTL 为什么能阻止路由环路
每经过一个三层转发设备，TTL 通常减 1。TTL 归零时，路由器丢弃数据包，并可能返回 ICMP Time Exceeded。

`traceroute` 或 Windows 的 `tracert` 正是利用这一机制逐跳发现路径。

不过，路径探测结果并不等于绝对真实的业务路径：

- 某些设备不响应 ICMP；

- 去程与回程可能不对称；

- ECMP 可能让不同探测包走不同路径；

- 防火墙或限速策略可能影响结果。

### 5.5 路由表如何决定下一跳
主机或路由器会根据路由表选择出口。最关键的规则是：

**最长前缀匹配。**

例如路由表中同时存在：

```
10.0.0.0/8 via A

10.10.0.0/16 via B

10.10.20.0/24 via C
```
目标 `10.10.20.8` 会匹配 `/24`，因此走 C。

如果没有更具体路由，就可能走默认路由：

```
0.0.0.0/0 via 192.168.1.1
```
Linux 查看路由：

```
ip route

ip route get 8.8.8.8
```
Windows 查看路由：

```
route print
```

### 5.6 ICMP：不仅仅是 ping
ICMP 用于传递网络控制和错误信息。常见类型包括：

- Echo Request / Echo Reply：`ping`；

- Destination Unreachable：目标不可达；

- Time Exceeded：TTL 超时；

- Packet Too Big：IPv6 路径 MTU 发现；

- Redirect：建议更合适的下一跳。
因此，“禁用所有 ICMP 会更安全”是一个危险的简单化结论。过度屏蔽 ICMP 可能破坏路径 MTU 发现和正常故障诊断。

### 5.7 IPv4 分片与路径 MTU
当 IP 包大于下一跳 MTU 时：

- IPv4 中，如果未设置 DF，路由器可能分片；

- 如果设置 DF，路由器会丢包并返回相关 ICMP 信息；

- IPv6 路由器不执行分片，源主机需要根据路径 MTU 调整发送大小。
分片会增加丢包影响和重组开销。现代网络通常更依赖路径 MTU 发现，尽量避免中间分片。

一个经典故障是 **PMTUD 黑洞**：小包正常，大包卡住，TLS 握手或文件上传异常。常见原因是链路 MTU 变小，但相关 ICMP 消息被防火墙错误拦截。

### 5.8 IPv6 需要掌握什么
IPv6 使用 128 位地址，例如：

```
2001:db8:1234:5678::10
```
重要特性包括：

- 地址空间巨大；

- 没有广播，主要使用组播和任播；

- 使用 NDP 代替 ARP；

- 路由器不负责分片；

- 常见链路本地地址前缀为 `fe80::/10`；

- 回环地址为 `::1`；

- 未指定地址为 `::`；

- ULA 地址范围为 `fc00::/7`。
IPv6 并不意味着“天然安全”。它仍然需要正确的防火墙、路由、地址规划和监控体系。

## 六、传输层：端口、Socket、TCP 与 UDP
IP 只能把数据送到主机，传输层还要把数据交给正确的进程。

### 6.1 端口是什么
端口号是 16 位整数，范围为 0～65535。

常见服务端口：

| 协议 | 默认端口 |
| --- | --- |
| SSH | 22 |
| DNS | 53 |
| HTTP | 80 |
| HTTPS | 443 |
| MySQL | 3306 |
| PostgreSQL | 5432 |
| Redis | 6379 |

IANA 常用分类为：

- 0～1023：系统端口；

- 1024～49151：用户端口；

- 49152～65535：动态或私有端口。
客户端主动发起连接时，操作系统通常会为它分配一个临时源端口。不同系统的实际临时端口范围可能不同。

### 6.2 一条连接如何被识别
TCP 连接通常由四元组标识：

```
源 IP、源端口、目的 IP、目的端口
```
在描述网络流时，常把协议号也加入，形成五元组：

```
源 IP、源端口、目的 IP、目的端口、传输层协议
```
这解释了为什么同一台服务器的 443 端口可以同时服务大量客户端：每个连接的四元组不同。

### 6.3 Socket 是什么
Socket 是操作系统提供给应用程序的网络编程接口。

服务端常见流程：

```
socket → bind → listen → accept → read/write → close
```
客户端常见流程：

```
socket → connect → read/write → close
```
注意：

- 监听 `127.0.0.1`，通常只允许本机访问；

- 监听 `0.0.0.0`，表示监听所有 IPv4 本地接口；

- IPv6 中常见监听地址为 `::`，其是否同时接受 IPv4 映射连接取决于系统配置。

## 七、UDP：简单、低开销，但不是“不可靠就没用”
UDP 是面向报文、无连接的传输协议。

### 7.1 UDP 的特点

- 不需要三次握手；

- 保留消息边界；

- 首部只有 8 字节；

- 不保证到达、顺序和去重；

- 没有内置流量控制和拥塞控制；

- 支持广播和组播场景。

### 7.2 UDP 适合什么场景

- DNS 查询；

- 实时音视频；

- 在线游戏；

- 监控指标或日志上报；

- DHCP；

- QUIC 的底层承载。
UDP 并不等于“完全不可靠”。应用可以在 UDP 之上自行实现确认、重传、顺序、拥塞控制和加密。QUIC 就是典型例子。

### 7.3 使用 UDP 时，应用要自己考虑什么

- 丢包如何处理；

- 乱序如何重排；

- 重复报文如何去重；

- 报文是否需要分片；

- 是否需要限速和拥塞控制；

- 是否需要防重放与身份认证；

- NAT 映射和会话保活。

## 八、TCP：可靠传输到底是怎样实现的
TCP 是面向连接、可靠、有序、全双工的字节流协议。

这句话里每个词都很重要：

- **面向连接**：通信前要建立状态；

- **可靠**：通过确认、重传、校验等机制降低丢失和损坏影响；

- **有序**：应用读取到的是按序字节流；

- **全双工**：双方可以同时发送数据；

- **字节流**：TCP 不保留应用写入时的消息边界。

### 8.1 三次握手为什么不是两次
假设客户端初始序列号为 `x`，服务器初始序列号为 `y`：

```
```
客户端 服务器

-------- SYN, Seq=x ------------>

<---- SYN+ACK, Seq=y, Ack=x+1 ----

-------- ACK, Ack=y+1 ----------->

连接建立
```
```
三次握手完成了几件事：

- 1. 双方确认彼此的收发能力；

- 2. 同步初始序列号；

- 3. 协商 MSS、窗口扩大、SACK、时间戳等 TCP 选项；

- 4. 防止陈旧的历史连接请求被误认为新连接。
“两次握手”无法让服务器确认客户端已经收到了服务器的初始序列号和连接参数。

### 8.2 序列号与确认号
TCP 给字节流编号。确认号表示：

“这个编号之前的字节我都收到了，下一步期待从这里开始。”

例如：

```
发送方发送 Seq=1000，长度 500 字节

接收方返回 Ack=1500
```
表示 1000～1499 已收到，下一字节应从 1500 开始。

SYN 和 FIN 各自会消耗一个序列号。

### 8.3 校验和
TCP 使用校验和检测传输中的比特错误。校验范围不仅包括 TCP 首部和数据，还包括由 IP 地址、协议号和长度等构成的伪首部，从而降低数据被错误交付给错误端点的风险。

校验和能发现很多随机错误，但它不是密码学完整性保护，不能抵御恶意篡改。需要安全传输时应使用 TLS、IPsec 等机制。

### 8.4 超时重传
发送方发出数据后，如果在重传超时时间 RTO 内没有收到确认，就会重传。

RTO 不是固定常数，而是根据往返时延 RTT 的测量动态估算，并考虑时延波动。网络抖动很大时，RTO 过小会导致不必要重传，过大则会让故障恢复变慢。

### 8.5 快速重传与选择确认
当接收端发现中间缺了一段数据，但后续数据已经到达时，会重复确认最后一个连续字节位置。发送端收到多个重复 ACK 后，可在 RTO 到期前触发快速重传。

SACK 允许接收端告诉发送端“哪些不连续的数据块已经收到”，让发送方只重传真正缺失的部分，而不是盲目回退重传大量数据。

### 8.6 流量控制：别把接收方淹没
接收端通过接收窗口 `rwnd` 告诉发送端自己还有多少缓冲空间。

如果应用读取太慢，接收缓冲区被占满，窗口可能降到 0。发送端会暂停发送，并周期性探测窗口是否重新打开。

流量控制解决的是：

**发送方太快，接收方来不及处理。**

### 8.7 拥塞控制：别把网络淹没
拥塞窗口 `cwnd` 反映发送方对网络承载能力的估计。

实际可发送的未确认数据量大致受两者共同限制：

```
可用发送窗口 ≈ min(rwnd, cwnd)
```
经典拥塞控制过程包括：

- 慢启动；

- 拥塞避免；

- 快速重传；

- 快速恢复。
流量控制和拥塞控制经常被混淆：

- `rwnd` 保护接收端；

- `cwnd` 保护网络路径。

### 8.8 带宽时延积：为什么“带宽很大”仍然跑不满
带宽时延积 BDP 表示一条路径中同时“在路上”的数据量：

```
BDP = 带宽 × RTT
```
例如：

```
带宽：100 Mbit/s

RTT：80 ms

BDP：100 × 0.08 = 8 Mbit ≈ 1 MB
```
要让链路跑满，发送窗口通常需要达到约 1 MB；如果窗口只有 64 KB，即使线路标称 100 Mbit/s，也可能无法充分利用。

这也是 TCP 窗口扩大选项在高带宽、高时延网络中非常重要的原因。

### 8.9 TCP 是字节流：“粘包”到底是什么
应用执行两次写入：

```
write("hello")

write("world")
```
接收端可能一次读到：

```
helloworld
```
也可能分多次读到：

```
hel

lowo

rld
```
这不是 TCP 出错，而是 TCP 本来就不保留消息边界。

正确做法是在应用层定义消息边界，例如：

- 1. 固定长度；

- 2. 特殊分隔符；

- 3. “长度字段 + 消息体”；

- 4. 使用自带帧格式的协议。
因此，“解决粘包”的本质是：**正确设计应用层协议，并正确处理半包、合包和多包。**

### 8.10 Nagle 算法与延迟确认
Nagle 算法会尽量合并小数据块，减少大量小包带来的网络和系统开销。接收端的延迟确认则可能短暂等待，以便合并 ACK 或随响应一起返回。

在交互式小报文场景中，两者组合可能增加延迟。部分应用会设置 `TCP_NODELAY` 禁用 Nagle，但这并不是万能优化：小包数量增加后，CPU、中断和网络开销也会增加。

### 8.11 TCP 连接关闭为什么常说“四次挥手”
TCP 是全双工的，两个方向需要分别关闭。

```
```
主动关闭方 被动关闭方

-------- FIN -------------------->

<------- ACK ---------------------

<------- FIN ---------------------

-------- ACK -------------------->
```
```
实际报文不一定严格是四个。若被动关闭方可以立即关闭，它可能把 ACK 和 FIN 合并发送。

### 8.12 TIME_WAIT 为什么不能随便删
主动关闭连接的一方通常进入 `TIME_WAIT`，持续时间通常与 2×MSL 有关，具体数值由实现决定。

它主要有两个作用：

- 1. 确保最后一个 ACK 丢失时，仍能再次响应对方重传的 FIN；

- 2. 让旧连接中的延迟报文在网络中消失，避免污染相同四元组的新连接。
大量 `TIME_WAIT` 不一定代表故障。应结合角色、连接创建速率、临时端口数量、是否使用连接池和是否能复用长连接判断。

### 8.13 CLOSE_WAIT 通常意味着什么
`CLOSE_WAIT` 表示：

- 对端已经发来 FIN；

- 本机内核已经确认；

- 但本地应用还没有关闭对应 Socket。
少量、短暂的 `CLOSE_WAIT` 正常。若长期堆积，通常要检查：

- 应用是否遗漏 `close()`；

- 异常分支是否未释放连接；

- 线程是否阻塞；

- 数据库、HTTP 客户端或连接池是否泄漏。

### 8.14 RST：为什么连接会被“重置”
RST 表示立即终止连接，常见原因包括：

- 访问了没有进程监听的 TCP 端口；

- 应用异常退出；

- 对已关闭连接继续发送数据；

- 中间防火墙或负载均衡器主动重置；

- 服务端主动拒绝当前请求；

- 连接状态在 NAT 或中间设备中已经过期。
`Connection reset by peer` 只能说明对端方向收到 RST，不能直接断定是业务程序主动发送。需要结合抓包位置和多点证据定位。

### 8.15 常见 TCP 状态

```
CLOSED

LISTEN

SYN-SENT

SYN-RECEIVED

ESTABLISHED

FIN-WAIT-1

FIN-WAIT-2

CLOSE-WAIT

CLOSING

LAST-ACK

TIME-WAIT
```
Linux 查看连接状态：

```
ss -ant

ss -s
```
统计某个状态：

```
ss -ant state time-wait | wc -l

ss -ant state close-wait | wc -l
```

## 九、NAT、防火墙与负载均衡
真实网络中，端到端路径往往还会经过各种中间设备。

### 9.1 NAT
NAT 会改写 IP 地址，有时也会改写端口。

常见类型：

- **SNAT**：改写源地址，常用于内网访问公网；

- **DNAT**：改写目的地址，常用于端口映射；

- **PAT/NAPT**：同时利用端口区分多个内部连接。
例如内网主机：

```
192.168.1.20:53000 → 203.0.113.10:443
```
经过 NAT 后可能变成：

```
198.51.100.8:62001 → 203.0.113.10:443
```
NAT 设备维护映射状态，因此空闲连接可能在映射超时后失效。

**NAT 不是安全机制的同义词。** 它可能带来一定隔离效果，但真正的访问控制来自防火墙策略、状态跟踪和安全边界设计。

### 9.2 防火墙
防火墙可基于以下信息放行或拒绝流量：

- 源/目的 IP；

- 源/目的端口；

- 协议；

- 连接状态；

- 应用层特征；

- 用户、进程、区域或安全标签。
常见现象：

- **立即返回拒绝或 RST**：可能是端口未监听，或防火墙主动拒绝；

- **长时间超时**：可能是静默丢弃、路由错误、返回路径异常或严重丢包。
但这只是经验，不是绝对规则。

### 9.3 四层与七层负载均衡
四层负载均衡主要根据 IP、端口和协议转发，通常不理解具体 HTTP 语义。

七层负载均衡可以根据：

- Host；

- URL 路径；

- Header；

- Cookie；

- 请求方法；

- 应用内容。
进行路由和治理。

排障时要明确：客户端连接的是后端服务本身，还是经过了 CDN、WAF、反向代理、服务网格或负载均衡器。

## 十、应用层常见协议，应该掌握到什么程度

### 10.1 DNS
DNS 不只是“域名转 IP”。常见记录包括：

- `A`：IPv4 地址；

- `AAAA`：IPv6 地址；

- `CNAME`：别名；

- `MX`：邮件交换；

- `TXT`：文本验证与策略信息；

- `NS`：权威 DNS；

- `PTR`：反向解析；

- `SRV`：服务发现。
DNS 故障可能来自：

- 本地缓存；

- 递归服务器；

- 权威记录；

- TTL 尚未过期；

- 分地域解析；

- DNS 污染或劫持；

- IPv4 与 IPv6 返回不一致；

- EDNS、DNSSEC 或报文大小问题。

### 10.2 DHCP
IPv4 DHCP 常用 DORA 流程：

```
Discover → Offer → Request → Acknowledge
```
它可以下发：

- IP 地址；

- 子网掩码；

- 默认网关；

- DNS 服务器；

- 租期；

- 其他网络参数。

### 10.3 HTTP 与 HTTPS
HTTP 定义请求与响应语义；HTTPS 是 HTTP 通过 TLS 保护后的传输方式。

排障时应把问题拆成不同层次：

- 1. DNS 是否解析正确；

- 2. IP 路由是否可达；

- 3. TCP 是否建立；

- 4. TLS 是否握手成功；

- 5. HTTP 状态码是否正常；

- 6. 业务响应是否符合预期。
不要把“网站打不开”当成一个不可拆分的问题。

## 十一、抓包：把猜测变成证据
网络排障最忌讳只靠感觉。抓包能让你看到每一步实际发生了什么。

### 11.1 tcpdump 常用命令
抓取指定端口：

```
tcpdump -i any -nn port 443
```
抓取指定主机：

```
tcpdump -i any -nn host 192.168.1.10
```
同时限制主机和端口：

```
tcpdump -i any -nn 'host 192.168.1.10 and port 443'
```
保存完整报文到文件：

```
tcpdump -i any -nn -s 0 -w capture.pcap 'tcp port 443'
```
读取抓包文件：

```
tcpdump -nn -r capture.pcap
```
常见 TCP 标志显示：

```
[S] SYN

[S.] SYN + ACK

[.] ACK

[P.] PSH + ACK

[F.] FIN + ACK

[R] RST
```

### 11.2 Wireshark 常用显示过滤器

```
tcp

udp

dns

icmp

ip.addr == 192.168.1.10

tcp.port == 443

tcp.flags.syn == 1

tcp.flags.reset == 1

tcp.analysis.retransmission

tcp.analysis.duplicate_ack

tcp.analysis.zero_window
```
注意区分：

- **捕获过滤器**：抓包时就决定哪些包被记录，通常使用 BPF 语法；

- **显示过滤器**：抓完后在 Wireshark 中筛选，语法不同。

### 11.3 如何识别一次正常 TCP 建连

```
1 Client → Server SYN

2 Server → Client SYN, ACK

3 Client → Server ACK
```
异常模式：

```
只有 SYN，不断重传
```
可能表示：

- 请求没到服务端；

- 服务端返回包没回来；

- 防火墙静默丢弃；

- 路由不通；

- 服务端负载过高；

- 抓包位置不在真实流量路径上。

```
SYN 后立即收到 RST
```
通常表示：

- 目标主机可达，但端口未监听；

- 主机或中间设备主动拒绝。

```
三次握手成功，但发送应用数据后无响应
```
说明网络层与 TCP 建连大概率正常，问题应进一步看 TLS、应用协议、后端依赖、反向代理或服务端处理。

### 11.4 为什么最好双端抓包
只在客户端抓包，只能看到“客户端观察到的事实”。

例如客户端重传一个包，可能是：

- 原包根本没到服务端；

- 原包到了，但 ACK 丢了；

- 服务端处理太慢；

- 中间设备丢弃；

- 抓包网卡卸载导致观察结果失真。
在客户端、服务端以及关键中间节点同时抓包，才能区分“哪里丢、谁没回、谁先关”。

### 11.5 网卡卸载为什么会让抓包看起来奇怪
现代网卡和内核会使用 TSO、GSO、GRO、LRO、校验和卸载等技术。抓包点可能位于分段或合并之前，因此你可能看到：

- 超过 MTU 的“大 TCP 包”；

- 本机发出的包显示校验和错误；

- 接收方向多个段被合并显示。
这不一定代表线上的真实报文异常。分析时要结合抓包位置和网卡卸载机制。

## 十二、网络排障的系统化方法
面对“网络不通”，不要一上来就重启、改内核参数或怀疑运营商。推荐按层排查。

### 第 1 层：本机配置与进程
检查：

```
ip addr

ip link

ip route

ss -lntup
```
关键问题：

- 网卡是否启用；

- IP、掩码、网关是否正确；

- 进程是否存活；

- 服务是否监听正确端口；

- 服务监听的是 `127.0.0.1` 还是 `0.0.0.0`；

- 本机防火墙是否放行。

### 第 2 层：同网段邻居与网关
检查：

```
ip neigh

ping -c 3 <gateway-ip>
```
关键问题：

- ARP/NDP 是否成功；

- 是否存在 IP 冲突；

- VLAN 是否正确；

- 默认网关是否可达。

### 第 3 层：路由与路径
检查：

```
ip route get <target-ip>

traceroute <target-ip>
```
关键问题：

- 是否选错出口；

- 是否缺少回程路由；

- 是否有策略路由；

- 是否存在网络环路；

- 是否经过了意外的代理、VPN 或隧道。

### 第 4 层：DNS
检查：

```
dig example.com

dig @8.8.8.8 example.com

dig +trace example.com
```
关键问题：

- 不同 DNS 返回是否一致；

- 域名是否解析到旧地址；

- TTL 是否尚未过期；

- 是否存在 CNAME 链；

- IPv6 记录是否导致访问路径变化。

### 第 5 层：端口与 TCP
检查：

```
nc -vz <host> <port>

ss -ant
```
Windows 可用：

```
Test-NetConnection <host> -Port <port>
```
关键问题：

- 三次握手是否完成；

- 是否被 RST；

- 是否只有单向流量；

- 是否发生重传；

- 是否耗尽临时端口或连接跟踪表。

### 第 6 层：TLS 与应用协议
检查：

```
curl -v https://example.com/

openssl s_client -connect example.com:443 -servername example.com
```
关键问题：

- 证书是否过期或域名不匹配；

- SNI 是否正确；

- TLS 版本与加密套件是否兼容；

- HTTP 状态码是什么；

- Host 头是否正确；

- 代理或网关是否返回错误。

### 第 7 层：性能
检查：

- RTT；

- 丢包率；

- 重传率；

- 吞吐量；

- 接收窗口和拥塞窗口；

- CPU、软中断和上下文切换；

- Socket 缓冲区；

- 应用处理时间；

- 队列积压；

- 中间设备超时。
**排障的核心原则：先确定故障层，再确定故障点；先收集证据，再修改配置。**

## 十三、六个高频故障场景

### 场景一：能 ping 通，但访问不了 443 端口
`ping` 通只说明：

- 某条 ICMP 路径可达；

- 目标或中间设备愿意响应 ICMP。
它不能证明：

- TCP 443 已监听；

- 防火墙放行 443；

- TLS 正常；

- HTTP 服务正常；

- 业务后端可用。
排查顺序：

```
nc -vz host 443

curl -vk https://host/

ss -lntp | grep ':443'

tcpdump -i any -nn 'host <client-ip> and port 443'
```

### 场景二：连接超时与 Connection refused 有什么区别
**Connection refused** 常见含义：

- 主机可达；

- 对应端口没有监听；

- 或防火墙主动返回拒绝。
**Connection timed out** 常见含义：

- 报文被静默丢弃；

- 路由或回程路由错误；

- 目标不可达；

- 网络严重丢包；

- 中间状态设备异常。
但最终仍要靠抓包确认，不能只根据错误文字下结论。

### 场景三：大量 TIME_WAIT
先问四个问题：

- 1. 谁在主动关闭连接；

- 2. 是否大量创建短连接；

- 3. 是否缺少连接池或 Keep-Alive；

- 4. 临时端口和 NAT 映射是否接近耗尽。
优化通常优先从架构入手：

- 复用连接；

- 使用连接池；

- 合理设置上游和负载均衡器的空闲超时；

- 减少无意义的短连接；

- 扩大可用源 IP 或端口资源。
不要把“缩短 TIME_WAIT”作为第一反应。

### 场景四：大量 CLOSE_WAIT
这通常更像应用资源释放问题。

排查：

```
ss -antp state close-wait

lsof -nP -iTCP -sTCP:CLOSE_WAIT
```
关注：

- 哪个进程持有连接；

- 哪段代码应该关闭连接；

- 异常处理是否遗漏清理；

- 是否存在阻塞调用或线程池耗尽；

- 连接池是否归还失败。

### 场景五：小请求正常，大文件上传失败
重点怀疑：

- 路径 MTU；

- VPN 或隧道额外封装；

- ICMP 被拦截；

- MSS 协商不合理；

- 代理或网关请求体限制；

- 应用超时。
Linux 可尝试不同大小的 DF 探测：

```
ping -M do -s 1472 <target-ip>
```
在典型 IPv4 环境中，1472 字节 ICMP 负载加 20 字节 IP 首部和 8 字节 ICMP 首部，合计 1500 字节。不同系统参数语义可能不同，使用前应查看本机帮助。

### 场景六：TCP 重传很多，究竟是谁的问题
重传不必然说明“发送方网络差”。可能原因包括：

- 前向链路丢包；

- 返回 ACK 丢包；

- 接收端处理或调度延迟；

- 队列拥塞；

- 网卡、驱动或物理链路错误；

- 中间设备限速或丢弃；

- 抓包点遗漏了报文；

- 包乱序被误判为丢包。
最好在链路两端同时抓包，并对齐五元组、序列号和时间戳。

## 十四、从“会用”到“精通”的 TCP 性能知识

### 14.1 延迟、带宽和吞吐不是一回事

- **带宽**：理论上单位时间可承载多少数据；

- **吞吐**：实际成功传输的数据量；

- **延迟**：数据到达需要多久；

- **RTT**：一次往返耗时；

- **抖动**：延迟变化；

- **丢包率**：报文丢失比例。
高带宽不等于低延迟，低延迟也不等于高吞吐。

### 14.2 慢启动对短连接的影响
TCP 初始不会立刻以链路最大速率发送，而是逐步探测网络容量。对于很短的请求，连接可能还没进入稳定高速阶段就已经结束。

因此，降低延迟和减少握手次数对短请求尤为重要：

- 连接复用；

- TLS 会话恢复；

- HTTP/2 多路复用；

- QUIC 的连接建立优化；

- 靠近用户部署边缘节点。

### 14.3 队头阻塞
TCP 必须按序向应用交付字节。如果前面一个段丢失，即使后续段已经到达，也要等待缺失数据重传。这就是 TCP 层面的队头阻塞。

HTTP/2 的多个流共享一条 TCP 连接，因此一个底层 TCP 丢包可能暂时影响多个流。QUIC 把不同应用流分开管理，某个流丢包通常不会阻塞其他流的数据交付，但单个流内部仍然需要有序传输。

### 14.4 Keepalive 与应用心跳不是一回事
TCP Keepalive 用于探测长期空闲连接是否仍然存在，但：

- 默认启用状态和时间参数因系统而异；

- 检测周期往往较长；

- 只能证明 TCP 层是否有响应；

- 不能证明应用业务逻辑健康。
应用心跳可以携带业务语义，通常更适合检测服务是否真正可用。

### 14.5 监听队列与 SYN Flood
服务端监听时，内核需要维护握手中的连接和等待应用 `accept()` 的已完成连接。具体队列结构和参数因操作系统实现而异。

当应用处理过慢、队列过小或遭遇 SYN Flood 时，可能出现：

- 新连接超时；

- SYN 重传；

- 队列溢出；

- SYN cookies 被启用；

- 业务连接建立速率下降。
排查时既要看网络，也要看应用是否及时调用 `accept()`。

### 14.6 拥塞控制算法
不同操作系统和网络环境可能使用不同拥塞控制算法，例如 CUBIC、BBR 等。它们对带宽探测、排队延迟和丢包的反应不同。

查看 Linux 可用与当前算法：

```
sysctl net.ipv4.tcp_available_congestion_control

sysctl net.ipv4.tcp_congestion_control
```
不要因为某个算法在一篇文章里表现好，就直接在生产环境全局替换。应通过真实业务流量、网络路径和回滚方案进行验证。

### 14.7 ECN
显式拥塞通知 ECN 允许网络设备在队列即将拥塞时标记报文，而不是必须通过丢包表达拥塞。发送端和接收端都支持、且路径中间设备正确处理时，可以更早做出拥塞反应。

### 14.8 QUIC 为什么值得关注
QUIC 通常运行在 UDP 之上，但它不是“简单 UDP 应用”。它实现了：

- 可靠传输；

- 拥塞控制；

- 流量控制；

- 多流；

- 连接迁移；

- 与 TLS 1.3 集成的加密握手。
HTTP/3 使用 QUIC。理解 TCP/IP 后再学习 QUIC，会更容易看清它解决了哪些问题，又引入了哪些新的运维和观测挑战。

## 十五、动手实验：亲眼看一次完整通信
以下实验可在 Linux 或 macOS 上完成。Windows 用户可以使用 WSL，或使用 Wireshark 配合 PowerShell 命令。

### 实验 1：观察本机 HTTP 连接
终端 A 启动一个临时 HTTP 服务：

```
python3 -m http.server 8080
```
终端 B 抓取回环接口流量。Linux 常见：

```
sudo tcpdump -i lo -nn 'tcp port 8080'
```
macOS 常见回环接口名也是 `lo0`：

```
sudo tcpdump -i lo0 -nn 'tcp port 8080'
```
终端 C 发起请求：

```
curl -v http://127.0.0.1:8080/
```
观察：

- 1. 三次握手；

- 2. HTTP 请求；

- 3. HTTP 响应；

- 4. FIN 或 RST；

- 5. 连接状态变化。

### 实验 2：查看域名解析链路

```
dig example.com

dig +trace example.com
```
对比：

- 本地递归结果；

- 根服务器、顶级域服务器和权威服务器的委派过程；

- A 与 AAAA 记录；

- TTL。

### 实验 3：观察路由选择

```
ip route

ip route get 1.1.1.1

traceroute 1.1.1.1
```
思考：

- 当前默认网关是什么；

- 实际从哪个接口出站；

- 源 IP 选成了什么；

- 路径是否经过 VPN 或策略路由。

### 实验 4：制造端口未监听
先确认某个本机端口没有进程监听，例如 9099：

```
ss -lnt | grep ':9099'
```
尝试连接：

```
nc -vz 127.0.0.1 9099
```
同时抓包：

```
sudo tcpdump -i lo -nn 'tcp port 9099'
```
你通常会看到 SYN 后立即返回 RST，从而直观看懂 `Connection refused`。

### 实验 5：验证 TCP 没有消息边界
可以分别编写一个简单客户端和服务端，让客户端连续发送多个小字符串，服务端用不同大小缓冲区读取。你会发现：一次 `send()` 并不对应一次 `recv()`。

这会比背诵“TCP 有粘包问题”更有价值，因为你真正理解了字节流语义。

## 十六、常见误区，一次说清

### 误区 1：TCP 有连接，所以绝不会丢数据
TCP 能在连接存续期间通过重传等机制提供可靠字节流，但应用仍需处理：

- 连接中断；

- 超时；

- 对端崩溃；

- 已发送但业务是否真正提交；

- 重试导致的重复操作。
“TCP 写成功”通常只代表数据进入了本机协议栈，不代表对端应用已经完成业务处理。

### 误区 2：ping 不通就是网络不通
ICMP 可能被禁用或限速，而 TCP/UDP 业务仍然可用。反过来，ping 通也不能证明特定端口和应用正常。

### 误区 3：交换机只看 MAC，路由器只看 IP
这是入门抽象。现代设备常集成多层能力，还可能执行 ACL、NAT、隧道、负载均衡和应用识别。

### 误区 4：TIME_WAIT 越少越好
TIME_WAIT 是 TCP 正确性机制。优化目标应该是合理的连接生命周期和资源使用，而不是盲目消灭状态。

### 误区 5：UDP 一定比 TCP 快
UDP 的协议开销更低，但应用若需要自行实现可靠性、重传、拥塞控制和加密，整体复杂度与性能未必更优。协议选择应匹配业务语义。

### 误区 6：HTTPS 之后网络问题就看不到了
加密隐藏了应用内容，但仍可观察：

- DNS；

- IP 和端口；

- TCP/QUIC 建连；

- RTT 与重传；

- TLS 握手元数据；

- 流量大小和时序；

- 服务端日志和指标。
只是排障更依赖端点日志、密钥日志、分布式追踪和多点观测。

### 误区 7：调大所有缓冲区就能提升性能
过大的缓冲区可能造成更深排队和更高延迟。参数优化必须结合 BDP、内存、连接规模、拥塞控制和真实业务测试。

## 十七、从入门到精通的学习路线

### 第一阶段：建立模型
目标：能解释一次请求如何从应用到网卡，再从网卡返回应用。

重点：

- TCP/IP 分层；

- 封装与解封装；

- IP、MAC、端口的区别；

- DNS、ARP/NDP、网关和路由；

- TCP 与 UDP 的基本差异。

### 第二阶段：掌握核心协议
目标：能读懂常见报文和连接状态。

重点：

- IPv4 子网与 CIDR；

- IPv6 基础；

- TCP 三次握手、序列号、ACK、窗口与重传；

- 四次挥手与状态机；

- ICMP、DNS、DHCP；

- NAT 与防火墙。

### 第三阶段：熟练使用工具
目标：从“猜原因”升级为“拿证据”。

重点：

- `ip`、`ss`、`dig`、`curl`、`nc`；

- `ping`、`traceroute`；

- `tcpdump` 与 Wireshark；

- 日志、指标与抓包时间线对齐；

- 双端抓包。

### 第四阶段：理解性能
目标：解释吞吐、延迟和丢包如何相互影响。

重点：

- RTT、BDP；

- 流量控制与拥塞控制；

- 慢启动；

- 重传与乱序；

- Socket 缓冲区；

- 网卡卸载；

- 连接复用与队头阻塞。

### 第五阶段：进入生产网络
目标：能处理跨主机、跨网段、跨云和跨地域问题。

重点：

- 策略路由与多网卡；

- VPN、隧道和 MTU；

- 四层/七层负载均衡；

- CDN、WAF、反向代理；

- 容器网络、Kubernetes Service 与 Ingress；

- 服务网格；

- 连接跟踪、NAT 表和临时端口；

- 可观测性与故障演练。
真正的“精通”不是背下所有字段，而是能回答三个问题：

- 1. 数据现在处于哪一层；

- 2. 这一层应该由谁负责；

- 3. 我能用什么证据证明问题在哪里。

## 十八、TCP/IP 排障速查表

| 现象 | 优先检查 | 常用工具 |
| --- | --- | --- |
| 域名无法解析 | DNS 配置、缓存、权威记录 | dig、nslookup |
| 能解析但不通 | 路由、网关、防火墙 | ip route、traceroute |
| ping 通但端口不通 | 监听地址、端口、防火墙 | ss、nc、tcpdump |
| 立即拒绝 | 端口未监听、主动 REJECT/RST | nc、抓包 |
| 连接超时 | 静默丢包、路由、回程路径 | 双端抓包、traceroute |
| TLS 失败 | 证书、SNI、协议版本 | curl -v、openssl s_client |
| 大量 TIME_WAIT | 短连接、主动关闭、端口资源 | ss -s、连接池指标 |
| 大量 CLOSE_WAIT | 应用未关闭 Socket | ss -antp、lsof |
| 小包正常、大包异常 | MTU、PMTUD、隧道 | ping -M do、抓包 |
| 吞吐低 | RTT、丢包、窗口、拥塞 | iperf3、抓包、系统指标 |
| 周期性断连 | NAT/LB 空闲超时、保活 | 设备配置、抓包、日志 |
| 重传高 | 丢包、乱序、处理延迟 | 双端抓包、接口错误计数 |

## 十九、结语：真正掌握 TCP/IP 的标志
学习 TCP/IP 最容易陷入两个极端：

- 只背概念，不会分析真实故障；

- 只会敲命令，不知道每条命令在验证什么。
更有效的方式，是把网络通信看成一条可验证的链路：

```
应用
↓
DNS 与配置
↓
Socket 与端口
↓
TCP/UDP
↓
IP 与路由
↓
ARP/NDP 与链路
↓
交换机、路由器、防火墙、NAT、负载均衡
↓
远端协议栈与应用
```
当你能从一个现象出发，快速判断应该检查哪一层；能通过日志、指标和抓包还原报文路径；能解释为什么连接建立、为什么重传、为什么关闭、为什么跑不满带宽——你才真正从“知道 TCP/IP”走向“会用 TCP/IP”。

网络世界看似复杂，但底层规则始终清晰：

**分层负责，逐跳转发，端到端协作；用状态理解连接，用报文验证事实。**
